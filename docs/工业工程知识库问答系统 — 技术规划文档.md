## 〇、Context（为什么做、为什么这么做）

### 0.1 触发原因
用户已有第一版 IE 知识图谱问答系统（Flask + Vue + MySQL + Neo4j + Ollama），但 `qa_service.py` 是空壳，整体也没用上 Karpathy llm-wiki 思路。现需重构为：**把 `llm-wiki-input` + `llm-wiki-output` 两个本地 skill 的方法论搬到 web 系统里，做成一个工业工程持续生长的知识库 + 问答 + 图谱产品**。

### 0.2 核心定位（三次纠偏后的最终版）
**这是一个"持续生长的工业工程知识库"，不是"教科书 RAG 问答系统"。**

- 任何 IE 相关 md 文档都可入库：教科书章节整理、知乎/小红书/公众号转 md、PPT 整理稿、企业案例、个人笔记、会议纪要……
- **没有"章节"概念**：一份 md 文件等同于一份**素材源**（source），不解析章节树、不切 chunk
- **领域是动态扩展的**：领域信息在 wiki 页面 frontmatter 的 `tags`/`domains` 字段里累积，不预设领域子目录
- **主问答不依赖向量 RAG**：走 wiki 检索 = index.md + 别名展开 grep + 读 3-5 份 wiki 页面 + 综合引用
- 节点版本化、跨素材源合并、双链双向、自动反链、可视化图谱、飞轮机制（gap-queue / hot-topics / followups / answer-quality）

> **澄清:"页面类型" vs "章节"**
> 文件系统下确实有 `wiki/entities/`、`wiki/topics/`、`wiki/sources/` 等目录,但这是按"wiki 页面在知识图谱中的角色"分类(实体节点 / 主题节点 / 素材摘要页),不是把一份 md 拆成多个章节文件。
> 一份用户上传的 md → 在 `wiki/sources/` 下生成**一份**素材摘要页 + 在 `wiki/entities/` 和 `wiki/topics/` 下产出/更新**若干**实体页与主题页;源 md 本身完整保存在 `raw/<source_type>/`,不被切分。
> 因此"没有章节"指的是**不切 chunk、不在 wiki/ 下按章节落盘多个分片**;"页面类型分目录"是输出侧的归类,不是输入侧的切分。

#### 性能指标（含测量方法）

| 指标 | 目标 | 测量方法 | 备注 |
|------|------|---------|------|
| 单批 100 篇 md(每篇 1 万字)首轮 ingest | ≤15 分钟 | 端到端计时,从 batch-ingest 触发到所有 job 状态 = done(P95) | DeepSeek V3 默认 |
| query 首字延迟 | ≤2.5 秒 | LLM 流式首字节时间(TTFB),不含前端渲染(P95) | DOMAIN_IE=true 时同样 |
| query 完整响应 | ≤8 秒 | 从请求发起到 SSE `done` 事件(P95) | - |

| 并发 query | ≥50 QPS | `ab -n 1000 -c 50`,错误率 ≤ 1% | P6 验收项 |

- **成本**：依据所选 provider；DeepSeek V3 默认下，单批 100 篇 < 1 元，月运营约 50 元
- **可扩展**：模型层、向量层、外部素材源（Web/PDF/PPT 转 md）都做成可插拔
- **可观测**：每 ingest 阶段流水线状态可见；query 评分写入 frontmatter；飞轮指标可在 status 看到
- **可维护**：节点变更不破坏旧引用（slug-redirect 表）；wiki 文件随时可手动编辑后再 sync 回索引

**缓存失效机制**(provider 工厂):
- 工厂以 `(provider, model, base_url, sha256(api_key))` 为缓存 key 持有 provider 实例
- `PUT /admin/config` 写入后调用 `factory.invalidate(target)`,下次请求重新构造
- 并发场景下用 `asyncio.Lock` 保护实例化,避免重复构造
- 不重启进程,变更秒级生效

> 实际状态(2026-05-19):14 张表的 alembic initial migration 已生成(`migrations/versions/0001_initial.py`),`alembic upgrade head` 在 dev SQLite 上验证全绿;**MySQL 实启验证推迟到 P2**(P1 期 dev 环境用 SQLite 跑迁移,生产 MySQL 容器已配置但未实启)。表名细节(如 `system_config` / `wiki_pages` / `graph_nodes` / `graph_edges` / `query_logs` / `answer_quality_scores` / `slug_redirects`)以 migration 为准。

#### 2.3.5 Neo4j（知识图谱镜像）
- 节点 label：`Entity`、`Topic`、`Source`、`Query`、`Synthesis`、`Comparison`
- 通用属性：`slug`（与 wiki 文件名同）、`title`、`tags`、`domains`、`updated_at`

**同步机制**:

- 失败重试 3 次(指数退避),仍失败则入死信队列(`audit_logs.kind='neo4j_sync_dlq'`),管理员从 GrowthDashboard 可手动重放

## 三、流程设计

### 3.1 ingest 流水线（5 阶段，比 v1.1 又简化一阶段——删了"章节解析"）

| 阶段 | 输入 | 输出 | 同步/异步 |
|------|------|------|----------|
| 1. 上传与登记 | .md + 元数据（标题、source_type、tags） | `documents` 行 + 文件落 `raw/{source_type}/` + content hash | 同步 |
| 2. **缓存检查** | raw 文件路径 | HIT → 跳过 LLM；MISS → 进入 Step1 | 同步（毫秒级） |
| 3. **Step 1：结构化分析** | 原文 + purpose.md + index.md 概要 + 现有 wiki 结构 | JSON：`{source_summary, entities[], topics[], connections[], contradictions[], new_vs_existing}`（带 confidence + evidence） | [async]（一次 LLM 调用） |
| 4. **Step 2：页面生成 + 跨素材源合并** | 原文 + Step1 JSON + 现有相关 wiki 页 | 素材摘要页（新建）+ 实体页（新建/更新）+ 主题页（新建/更新）+ index.md 增量 + log.md 追加 + 缓存更新 | [async]（一次 LLM 调用） |
| 5. **后处理** | 上述产物 | 反链表 wiki_links 增量更新 + Neo4j 同步 + 实体相似度合并候选检测（向量库）+ graph-data.json 标记需重建 | [async] |

关键设计：
- **没有"章节解析"** —— md 直接当一份素材源整体处理，章节结构由 LLM 在 Step1 内部理解，不外化为 chunk
- **Step1 / Step2 解耦** —— Step1 失败可降级到单步 ingest（旧版兼容）
- **缓存检查在最前** —— 内容 hash 命中直接复用已有页面，不再调 LLM
- **跨素材源合并在 Step2 内** —— 同名/相似实体不新建,向已有页追加"## 不同素材中的观点"段
- **隐私自查清单** —— 上传时前端弹窗强制确认（手机号 / 身份证 / API key / 密码），用户回 y 才进流水线

#### 3.1.1 Step1 输出 JSON schema(契约)

```jsonc
{
  "source_summary": {                          // 必填
    "title": "string",                         // 素材标题
    "kind": "textbook|article|note|case|other",
    "domain_tags": ["人因工程", "..."],         // ≥1
    "key_takeaways": ["string", "..."]          // 3-7 条核心观点
  },
  "entities": [                                // 0+ 个实体节点候选
    {
      "name": "string",                        // 必填,中文优先
      "aliases": ["string", "..."],            // 别名/英文/缩写
      "kind": "method|tool|concept|person|org|metric",
      "brief": "string",                       // ≤200 字
      "evidence": "string",                    // 在原文的位置或引语
      "confidence": "EXTRACTED|INFERRED|AMBIGUOUS",
      "domain_tags": ["string", "..."]
    }
  ],
  "topics": [                                  // 0+ 个主题节点候选
    {
      "name": "string",
      "scope": "string",                       // 主题边界说明
      "related_entities": ["entity_name", "..."],
      "evidence": "string",
      "confidence": "EXTRACTED|INFERRED|AMBIGUOUS"
    }
  ],
  "connections": [                             // 0+ 条关系
    {
      "src": "entity_or_topic_name",
      "dst": "entity_or_topic_name",
      "rel_type": "实现|依赖|对比|矛盾|衍生|<schema 扩展>",
      "evidence": "string",
      "confidence": "EXTRACTED|INFERRED|AMBIGUOUS"
    }
  ],
  "contradictions": [                          // 0+ 条与现有 wiki 矛盾的主张
    {
      "with_page": "slug",
      "claim_old": "string",
      "claim_new": "string",
      "evidence": "string"
    }
  ],
  "new_vs_existing": {                         // 必填
    "new_entity_names": ["string", "..."],
    "matched_entity_pages": [{"name": "string", "slug": "string", "match_kind": "exact|alias|similarity"}],
    "new_topic_names": ["string", "..."],
    "matched_topic_pages": [{"name": "string", "slug": "string"}]
  }
}
```

校验规则:`services/ingestion/validator.py` 跑 JSON schema 校验,失败重试一次后写 `audit_logs` 并把 job 置 `failed_step1`,管理员可在前端"摄入历史"页面手动重跑或修订。

#### 3.1.2 Step2 输出契约

Step2 不返回结构化 JSON,而是**直接产出/更新 wiki 页面文件**:
- 新建/更新 `wiki/sources/{date}-{slug}.md`(每份素材一份摘要页)
- 新建/更新 `wiki/entities/{slug}.md` × N(对每个 `new_entity_names`)
- 更新 `wiki/entities/{slug}.md` × M(对每个 `matched_entity_pages`,在"## 不同素材中的观点 / ### 来源:{source_slug}"区追加)
- 新建/更新 `wiki/topics/{slug}.md` × K
- 增量更新 `index.md` 与 `log.md`
- 写 `wiki_links` / `wiki_pages` 索引镜像
- 触发后处理(向量化、Neo4j 同步、graph-data.json 标记重建)

Step2 用模板化生成(`app/prompts/templates/entity.md` / `topic.md` / `source.md`),LLM 仅填充正文段;frontmatter 由后端组装(slug、updated、version、sources[]、confidence)。

#### 3.1.3 隐私自查清单(检测算法)

**检测时机**:`POST /ingestion/upload` 成功落 raw 后、未触发 Step1 前。

**检测规则**(`services/ingestion/privacy_check.py`):

| 类目 | 正则(简化) | 命中行为 |
|------|------|---------|
| 手机号 | `(?<!\d)1[3-9]\d{9}(?!\d)` | 标黄,要求确认 |
| 身份证 | `(?<!\d)[1-9]\d{5}(18\|19\|20)\d{2}(0[1-9]\|1[0-2])(0[1-9]\|[12]\d\|3[01])\d{3}[\dXx](?!\d)` | 标红,强制脱敏或放弃 |
| 邮箱 | `[\w.+-]+@[\w-]+\.[\w.-]+` | 标黄,要求确认 |
| 常见 API key 前缀 | `(sk-\|gsk_\|xai-\|hf_\|ghp_\|github_pat_)[A-Za-z0-9_-]{16,}` | 标红,强制删除 |
| 银行卡 | `(?<!\d)\d{16,19}(?!\d)` | 标黄(易误报,提示用户人工确认) |
| URL 中的 token | `[?&](token\|access_token\|api_key)=[A-Za-z0-9_-]+` | 标红 |

**返回结构**(给前端):
```json
{
  "ok": false,
  "hits": [
    {"line": 42, "category": "phone", "snippet": "联系电话:138****", "level": "warn"},
    {"line": 87, "category": "api_key", "snippet": "sk-xxxx", "level": "block"}
  ],
  "block_count": 1,
  "warn_count": 1
}
```
- `block` 类必须用户编辑后重新上传,不允许跳过
- `warn` 类前端弹窗"我已确认无敏感信息"复选框后才能 ingest
- 命中位置回写 `documents.privacy_check_json`,审计日志记录用户决策

### 3.2 跨素材源节点合并机制（核心生长逻辑）

```
新 md ingest → Step1 输出 entities[]
   ↓
对每个候选 entity：
   先按字面 slug 匹配 wiki/entities/ 下文件
   ├─ 命中 → 视为同一节点
   ↓
   未命中：BGE-M3 向量与现有实体页 brief 比对
   ├─ 余弦 ≥ 0.92 → 视为同一节点（自动合并）
   ├─ 0.75 ≤ 余弦 < 0.92 → 标记"疑似合并候选",写 gap-queue（origin=merge_suggestion），等管理员审核
   └─ 余弦 < 0.75 → 新建节点
   ↓
合并时：
   - 实体页正文：在"## 不同素材中的观点 / ### 来源：{source_slug}"区追加新主张
   - frontmatter `sources[]`：append 新 source slug
   - frontmatter `updated`：刷新时间戳
   - frontmatter `version`：+1
   - 在 `wiki_node_versions` 表里记录 diff
```

**阈值来源与调参**:0.92 / 0.75 沿用旧项目 `embedding_service.py` 的实测值(IE 领域中文术语,F1≈0.88);P4 启动 answer-quality 评分后回顾误合并/漏合并案例,在 `.wiki-schema.md` 成长配置中暴露 `merge_threshold_auto` / `merge_threshold_suggest` 两个键供管理员调参。

`hot-topics.md` 的别名归并 + `.wiki-schema.md` 别名词表共同保证：术语异写不会重复造节点。

### 3.3 query 流程（**不走 chunk 级 RAG**，对齐 llm-wiki-output 工作流 1）

> **再次澄清**:此流程**完全不调用 Chroma 向量检索**。Chroma 只在 ingest 阶段(3.2 跨素材源合并)和图谱节点向量(3.5)被使用。query 走文件系统 grep + 别名展开 + 读 wiki 页面 + LLM 综合。

| 步 | 算法 | 输入 | 输出 |
|----|-----|------|------|
| 1 | 读 .wiki-schema.md → 定 WIKI_LANG / DOMAIN_IE / 别名词表 | - | 上下文 |
| 2 | 读 index.md 了解知识库全貌 | - | 全局概要 |
| 3 | **别名展开**：用户问题关键词命中某别名组 → 该组所有同义词都纳入搜索（不跨组传递、自动去重） | 问题 + 别名词表 | 扩展关键词列表 |
| 4 | **grep**：在 `wiki/` 下搜所有关键词；按相关性排序（文件名精确 > index 命中 > 正文命中次数） | 扩展关键词 | top 3-5 候选页面 + 命中段落（每关键词最多 3 段，总不超 15 段） |
| 5 | **读页**：读取候选页面（单页超 2000 字时只读 frontmatter + 前 500 字 + 命中段落前后 3 行） | 候选页 | 阅读上下文 |
| 6 | **IE 领域风格调整**：DOMAIN_IE=true 时按规则路由到方法论 / 概念 / 通用三种 prompt(详见 3.3.1) | 上下文 + 问题 | LLM prompt |
| 7 | **LLM 综合**（多 provider 流式）：system prompt 强约束"只能用 context，引用用 [[页面名]]" | prompt | 流式 token |
| 8 | **answer-quality 评分**：见 3.3.2 公式 | 答案 + 引用列表 + graph-data.json | 评分 JSON |
| 9 | **判断持久化**：cited_sources ≥3 提示用户保存；<3 且 gap_flag=true 不持久化但记 gap | 评分 | 决策 |
| 10 | **重复检测 + 写 query 页**：搜 `wiki/queries/` 同主题；命中 → 询问更新还是新建；新建用 `wiki/queries/{date}-{hash}.md` | 答案 + 评分 | query 页 + frontmatter（含 user_question / answer_quality / tier / gap_flag / followups） |
| 11 | **Gap 记账**：gap_flag=true 时追加 gap-queue 条目（id / origin=query / suggested_seeds / status=open） | 评分 | gap-queue.md 增量 |
| 12 | **更新 index.md / log.md** | - | 索引刷新 |

**幻觉抑制**：context 完全没命中时返回"知识库未覆盖"，不自由生成。

#### 3.3.1 IE 领域风格路由(DOMAIN_IE=true 时)

| 问题类型 | 关键词命中(任一) | prompt 模板 | 答题骨架 |
|---------|----------------|-----------|---------|
| 方法论类 | 怎么 / 如何 / 步骤 / 实施 / 落地 / 流程 / 操作 | `query_ie_method.md` | 目的 → 适用前提 → 步骤 → 量化指标 → 典型陷阱 |
| 概念类 | 是什么 / 含义 / 区别 / 关系 / 区分 / 对比 / 异同 | `query_ie_concept.md` | 定义 → 核心逻辑 → 典型应用场景 → 与近义概念的区别 |
| 通用 | 以上都不命中 | `query_general.md` | 自由组织,但要求引用 [[页面名]] |

匹配规则:正则匹配问题文本(中英文兼容,大小写忽略);**多类命中时按"方法论 > 概念 > 通用"优先级**(因为方法论问答的结构化要求更强)。

#### 3.3.2 answer-quality 评分公式

```
score = 0.4 * cited_normalized
      + 0.3 * confidence_avg
      + 0.2 * (1 - alias_miss_ratio)
      + 0.1 * (1 - broken_link_ratio)

cited_normalized   = min(cited_sources, 5) / 5      # 引用页面数(去重),封顶 5
confidence_avg     = mean(被引用页 frontmatter.confidence_score)  # EXTRACTED=1.0 / INFERRED=0.6 / AMBIGUOUS=0.3
alias_miss_ratio   = 用户提问关键词中未在 wiki 命中的别名比例
broken_link_ratio  = 答案中 [[X]] 链接 wiki/ 下不存在的比例
```

**tier 划分**:
- `score ≥ 0.8` → `tier = "high"`
- `0.6 ≤ score < 0.8` → `tier = "medium"`
- `score < 0.6` → `tier = "low"`

**gap_flag 触发**(满足任一):
- `score < 0.6`
- `cited_sources < 3`
- `alias_miss_ratio > 0.3`(用户提问的关键词知识库覆盖严重不足)
- 答案中含模型自承"我不太确定/未找到资料"等 hedge 表达(关键词列表见 `services/query/scoring.py`)

评分 + tier + gap_flag 三个字段写入 query 页 frontmatter,并镜像到 MySQL `answer_quality_scores` 表;`gap_flag=true` 触发 gap-queue 入队(状态机见 3.6.1)。

> 实际状态(2026-05-19):前端 Query.vue 已经预留了 score / tier / gap_flag 的展示位(P1.5 完成),后端公式实现在 P4(`services/query/scoring.py`)。

### 3.4 digest 流程（深度报告 / 对比表 / 时间线 三模板）

按触发关键词路由到三种模板（对应 llm-wiki-output 模板 A/B/C）：

#### 3.4.1 三模板路由规则

| 模板 | 触发关键词(任一,大小写忽略) | prompt 模板 | 输出页类型 | 输出骨架 |
|------|--------------|-----------|---------|---------|
| **deep-dive** | 深度分析 / 综述 / digest / 全面讲讲 / 系统梳理 / 总览 | `digest_deep_dive.md` | `wiki/synthesis/{slug}.md` | 背景概述 / 核心观点 / 不同视角对比 / 知识脉络 / 尚待解决的问题 / 相关页面 |
| **comparison** | 对比 / 区别 / 异同 / VS / 比较 / 优劣 | `digest_comparison.md` | `wiki/comparisons/{slug}.md`(也可写 synthesis/) | 对比对象 / 对比表(IE 模式 6 维:核心观点 / 适用场景 / 量化指标 / 实施成本 / 典型陷阱 / 来源素材) / 关键差异 / 相关页面 |
| **timeline** | 时间线 / 按时间排列 / 发展史 / 演进 / 历史 | `digest_timeline.md` | `wiki/synthesis/{slug}.md` | Mermaid gantt 或纯文字时间线 / 事件说明 / 相关页面 |

**多关键词同时命中时优先级**:`comparison > timeline > deep-dive`(因为 comparison 和 timeline 的结构化要求最强,deep-dive 是兜底)。

**用户也可在 `POST /digest` 请求体里手动指定 `template`** 字段,跳过自动路由。

#### 3.4.2 评分与 gap 入队

每份 digest 落盘后:
- **deep-dive**:查 5 个标准 H2(背景 / 核心观点 / 视角对比 / 知识脉络 / 尚待解决) 缺几个 → `sections_missing`;`sections_missing > 1` 触发 `gap_flag=true`
- **comparison**:对比表算 `fill_rate = 非空单元格 / (行数 × 列数)`;`fill_rate < 0.7` 触发 `gap_flag=true`,**逐空格** append gap-queue(每个空格一条,suggested_seeds = 行标题 + 列标题)
- **timeline**:事件密度 `events_per_decade < 2` 时标记 `sparse=true`,但不强制入 gap

`followups` 字段从 deep-dive "## 尚待解决的问题"段同步进 frontmatter,供 followups 队列聚合。

### 3.5 graph 流程（消费 graph-data.json）

| 步 | 算法 | 输出 |
|----|-----|------|
| 1 | 扫 `wiki/**/*.md`，解析每行 `[[X]]` | 边列表 |
| 2 | 解析 `<!-- confidence: EXTRACTED/INFERRED/AMBIGUOUS -->` 注释 | 边置信度 |
| 3 | 计算 3 信号边权重（共引强度 / 来源重叠 / 类型亲和度） | 边权重 |
| 4 | Louvain 社区发现 | 节点 community_id |
| 5 | 规则 insights：惊人连接（跨社区高权重边） / 桥节点（连接多社区）/ 知识缺口（度数低）/ 稀疏社区 | insights |
| 6 | 写 `wiki/graph-data.json` | - |
| 7 | 前端 Vue 实时消费（替代 llm-wiki 的 knowledge-graph.html） | 3D 图谱可视化 |

前端 3D 图谱：
- 节点点击 → 右侧抽屉渲染 .md 全文 + 反链 + 引用
- query 完成后接收 path payload → 高亮本次问答涉及的节点 + 边
- insights 面板：列出孤立节点、桥节点等，可一键加入 gap-queue

### 3.6 飞轮机制（覆盖 llm-wiki-output 全部能力）

```
query → answer-quality 评分 → cited_sources < 3 / gap_flag=true → gap-queue 入队
digest deep-dive → sections_missing → gap-queue 入队
digest comparison → 空单元格 → 逐格 gap-queue 入队
graph → isolated_nodes / sparse_communities → 用户确认后入 gap-queue
                              ↓
                        gap-queue.md
                              ↓
                  管理员从队列挑一条 → ingest（带 suggested_seeds）→ 状态变 resolved
```

trend / followups / hot-topics 都基于 wiki/queries/ 和 wiki/synthesis/ 的 frontmatter 周期性聚合。

#### 3.6.1 gap-queue 状态机

```
[open]  ───── admin 标"在做"   ──→  [in_progress]
   │                                      │
   │ admin 直接关闭(无效/重复)             │ ingest 完成 + 关联素材入库
   ▼                                      ▼
[dismissed]                            [resolved]
                                          │
                                          │ 7 天后 + answer-quality 仍 < 0.6
                                          ▼
                                      [reopened] → 回到 open
```

**字段**(`gap_queue` 表 + `_growth/gap-queue.md` 镜像):
- `id` / `origin`(query / digest / comparison / merge_suggestion / graph_isolated / graph_sparse_community / manual)
- `created_at` / `updated_at` / `resolved_at`
- `user_question` / `query_page` / `digest_page`(任一,看 origin)
- `gap_reasons`(自由文本,LLM 生成)
- `suggested_seeds`(JSON 数组:推荐用户去搜哪些关键词、哪些素材源)
- `status` ∈ open / in_progress / resolved / dismissed / reopened
- `resolved_by`(user_id) / `resolved_via_ingest_job_id`(关联 ingest job)

**消化路径**(P5):
1. 管理员在 GrowthDashboard 看到 open 队列,挑一条 → 状态变 in_progress
2. 后端用 `suggested_seeds` 启动 firecrawl 抓取(可选)或提示管理员手动准备 md
3. ingest 完成后,系统检查这条 gap 关联的 query/digest 重新跑一遍 answer-quality:通过则 resolved,仍不通过则保持 in_progress
4. 7 天定时任务扫 resolved 项:对应 query 重测,score 仍 < 0.6 则 reopened

#### 3.6.2 trend / followups / hot-topics 聚合

- **trend**:每 30 分钟从 `wiki/queries/` 扫 frontmatter,按主题聚合 `query_count_30d`,`gap_share`(gap_flag=true 占比);`query_count ≥ 3 且 gap_share > 0.5` → 自动加入 hot-topics 候选
- **hot-topics**:管理员审核 trend 输出后落盘 `_growth/hot-topics.md`,影响 ingest 时实体合并优先级
- **followups**:每天聚合 `wiki/synthesis/` 中 deep-dive 报告的 `followups` 字段,按 age_days 排序,管理员可一键转 gap-queue

## 六、关键技术风险与对策

| # | 风险 | 对策 |
|---|------|------|
| R1 | md 文档质量参差（frontmatter 缺失、格式乱） | 上传时校验必填 frontmatter（title / source_type / tags），异常给提示但不阻塞；提供模板下载；管理员可在前端 WikiViewer 编辑器修订 |
| R2 | LLM Step1 抽 entities 可靠性 | 三层校验：(a) Step1 prompt 强约束 + JSON schema validate；(b) 失败降级到单步 ingest（旧版兼容）；(c) Step2 跨素材源合并时再做相似度去重 |
| R3 | 多 provider 抽象层兼容性（不同 provider 参数不同） | 统一接口 + 各 provider 内部翻译参数；每个 provider 加 connection test；配置变更不重启即生效（应用层缓存 + invalidate） |
| R4 | API key 泄露 | Fernet 对称加密(P1 已落地);GET 返回时屏蔽（前 4 位 + ****）；审计日志记录 key 变更;Fernet key 文件不入 git,异地加密备份 |
| R5 | [[wikilink]] 自动维护 | 后台 link_resolver：扫每个 .md，候选实体 mention 与 slug 表精确+模糊匹配，命中即替换为双链；同步写 `wiki_links`；改名通过 slug-redirect 表保稳定 |
| R6 | 没有 chunk 级 RAG，长文 grep 命中段落不够时 LLM 拿不到全文 | 单页超 2000 字时只读 frontmatter + 前 500 字 + 命中段落前后 3 行（对齐 llm-wiki-output 现行规则）；query 答得不好会自动入 gap-queue，触发后续 ingest 增量 |
| R7 | 知识库生长后节点爆炸 + 别名同义词重复 | 阈值合并 + .wiki-schema.md 别名词表（前端可编辑） + 周期 lint 检测孤立 / 重复 / 过相似 |
| R8 | 关系类型由用户/管理员维护，前期可能空 | 在 .wiki-schema.md 预填 5 个默认关系类型（实现 / 依赖 / 对比 / 矛盾 / 衍生）；用户在 SchemaEditor 可扩展 |
| R9 | DOMAIN_IE 模式下回答风格调整影响通用性 | 仅在 .wiki-schema.md 主题字段含"工业工程/IE"时启用；其他主题自动走通用模板 |
| R10 | 飞轮机制（gap-queue / hot-topics / followups）首期数据为空 | MVP 内不要求飞轮全跑通；先实现 query→gap-queue 闭环，其他随数据积累再开 |
| R11 | 成本（依赖所选 provider） | provider 对比表（见下） + 前端配置页面显示当前 provider 估算单价 + 超阈值告警 |
| R12 | **Neo4j GDS 社区版限制** | Louvain 在社区版可用,但 PageRank / nodeSimilarity 等高级算法限企业版;若 P5 触达限制,改用 networkx + python-louvain(P1 已装,纯 Python 实现) |
| R13 | **DeepSeek API 配额/可用性故障** | (a) provider 配置页面预留"二级 provider"字段;(b) 主 provider 调用失败 3 次自动切二级;(c) `audit_logs` 记录切换事件;(d) GrowthDashboard 显示当前主 provider 状态 |
| R14 | **同一 wiki 页面并发写冲突** | (a) ingest job 在 Step2 阶段对每个 slug 取 `data/cache/locks/{slug}.lock` 文件级 advisory lock(超时 60s);(b) 手动 PUT /wiki/pages 同样需取锁;(c) 锁冲突时返回 423 Locked,前端轮询重试 |

### 8.4 LLM 输出验证策略

- Step1 / Step2 输出走 JSON schema 校验(`services/ingestion/validator.py`),失败重试 1 次
- 重试仍失败 → job 置 `failed_step1` 状态,写 `audit_logs` 记录 prompt + 响应 + 错误,不阻塞其他 job
- 管理员可在前端"摄入历史"页查看失败 job 的 prompt/response,选择手动重跑 / 修订 / 放弃
- 周期性聚合失败模式(每周聚合 `failed_step1` 的错误关键词),反哺到 prompt 优化

### 8.5 错误处理与降级策略

| 失败场景 | 行为 |
|---------|------|
| 主 LLM provider 调用超时/429/5xx | 重试 3 次(指数退避 1s/2s/4s) → 仍失败切二级 provider → 仍失败标 job 失败,写 audit_logs |
| LLM 输出 JSON schema 校验失败 | 重试 1 次(prompt 加"请严格按 schema 返回") → 仍失败标 job `failed_step1` |
| Embedding provider 不可用 | 跳过相似度合并,所有候选实体一律新建(后续可由管理员合并);记 audit_logs 提示 |
| Neo4j 不可用 | 主问答不阻塞(走文件系统);Neo4j 同步入死信队列,GrowthDashboard 红灯告警 |
| MySQL 不可用 | 全停服(关键依赖)+ Nginx 返回 503 |
| Chroma 不可用 | 跳过实体相似度合并(降级到字面匹配),记 audit_logs |
| wiki 文件落盘失败(磁盘满/权限) | 全停服(关键依赖)+ Nginx 返回 503 + 管理员告警 |
| 文件锁冲突(R14) | 返回 423 Locked,前端 5s 后轮询重试,3 次仍冲突提示用户稍后再试 |
| SSE 客户端断开 | 后端通过 `asyncio.shield` 让 LLM 调用跑完,answer 落 query 页(允许"完成度=完整"标记)即使前端没收到 |

> P6 章节中提到的"监控 + 备份"在这里集中展开。P1-P5 期可不实装,但接口与日志格式从 P2 起就按本节约定写。

### 11.1 日志策略

- 所有后端日志走 loguru,统一格式:`{time} | {level} | {module}:{func}:{line} | {message}`
- 关键路径加 `correlation_id`(一次 ingest job / 一次 query 的全链路 trace ID)
- 日志分文件:`backend/logs/app.log`(常规)、`backend/logs/audit.log`(`audit_logs` 表镜像,便于 grep)、`backend/logs/llm.log`(LLM 调用 prompt + response 的脱敏摘要,P4 起开启)
- 日志 rotate:每天分文件,保留 14 天
- P6 起用 loguru 的 sink 把 ERROR 及以上推到 Prometheus exporter

### 11.2 监控指标

| 指标 | 维度 | 采集方式 |
|------|------|---------|
| API 请求量 | 端点 / 状态码 | FastAPI middleware |
| API P95 延迟 | 端点 | FastAPI middleware |
| LLM 调用成功率 | provider / 模型 | `services/llm/factory.py` 包装 |
| LLM 调用 P95 延迟(首字 + 完整) | provider / 模型 | 同上 |
| ingest job 通过率 | 阶段(step1 / step2 / postprocess) | `ingestion_jobs` 表聚合 |
| wiki 页面数增长曲线 | kind(entity/topic/source/...) | 每小时统计 |
| gap-queue 堆积量 | origin / status | `gap_queue` 表 count |
| answer-quality tier 分布 | 7 天滑动窗 | `answer_quality_scores` 表 |
| Neo4j / MySQL / Chroma 连接池使用率 | - | 各 client 暴露 |

P6 用 Prometheus + Grafana 看板;P5 起在 GrowthDashboard 内嵌简化版指标卡(用不依赖 Prometheus 的纯 SQL 聚合)。
