# 合并方案：知识库 + 绘图平台

> 目标：把 `D:\kg-qa-ie`（工业工程知识库问答）和 `C:\Users\lenovo\Desktop\zhihuitu`（智绘图 AI 制图平台）合成一个系统。
> 主干 = 知识库；在它基础上迁入绘图能力；新做一个门户首页切换两个平台。
> 编写日期：2026-08-04

## 1. 结论先行

这不是"成熟项目 + 半成品"的合并，而是**两个都在运行的系统对接**。两边的领域天然咬合——智绘图正在做产线平衡和 SOP 生成，知识库是工业工程知识体系——这是本次合并最有价值的部分，不只是把代码拼在一起。

形态定为：**单前端 + 双后端**。后端保持两个独立进程，前端合成一个应用、一套导航、一次登录。

核心判断依据：知识库后端用 SQLAlchemy **同步**，绘图后端用 **async**。两者在同一个 FastAPI 进程里混跑会出现事件循环阻塞，硬合成单后端要大改一边。保持双进程是正确选择，不是妥协。

## 3. 关键技术核实（已验证）

这四项直接决定接线方式，均已在代码中确认。

### 3.1 JWT 完全兼容 ✅

两边签发的令牌都是 `sub = str(user.id)`、算法 HS256。

```python
# kb: backend/app/core/security.py
payload = {"sub": str(subject), "iat": ..., "exp": ..., "type": "access"}
jwt.encode(payload, settings.jwt_secret, algorithm="HS256")   # PyJWT

# chart: backend/app/api/v1/auth.py:44
token = create_access_token({"sub": str(user.id)})            # python-jose
```

知识库多签了 `iat` 和 `type`，但**两边解码时都不校验这些额外字段**。共享同一密钥后令牌即可互认，无需字段映射。JWT 库不同（PyJWT vs python-jose）但线上格式一致，不影响互操作。

### 3.2 端口冲突此前已解决 ✅

绘图侧 `docker-compose.override.yml` 里写着：

```yaml
# 宿主 8000 已被其他服务占用（IPv4 端冲突），改用 8010 暴露智绘图后端。
- "127.0.0.1:8010:8000"
```

那个占用 8000 的服务就是知识库。`frontend/vite.config.ts` 的代理也已指向 8010。

**结论：知识库保 8000、绘图保 8010，端口配置一行都不用改。**

### 3.3 Neo4j 与 Chroma 都是软依赖 ✅

- **Neo4j**：`neo4j_client.connect()` 返回布尔值，连不上只打 `warning`；不在启动生命周期（`lifespan`）里。缺它只是图谱功能降级。
- **Chroma**：支持内嵌（`PersistentClient`）和独立服务（`HttpClient`）两种模式。`services/query/hybrid.py` 里向量检索包在 try/except 内，源码注释写明 *"semantic retrieval is an optional enhancement"*，失败退回词法检索。

**第一阶段 docker-compose 可以先不拉这两个服务。**

> 修正一处早期判断：向量检索**现在确实在问答主路径上**（`query/vector_index.py` + `query/hybrid.py`），只是可优雅降级。不是"不在查询路径上"。

### 3.4 统一用 npm ✅

知识库只有 `package-lock.json`。绘图侧两个锁文件并存，但 npm 的（5月5日）比 pnpm 的（5月1日）新。

**处理：删除 `zhihuitu/frontend/pnpm-lock.yaml`，统一 npm。**

## 4. 必须优先处理：知识库 RBAC 是空壳

```python
# kb: backend/app/core/deps.py:86
def require_admin(user_id: Annotated[int, Depends(get_current_user_id)]) -> int:
    """管理员权限：dev 模式下任何用户都通过；prod 模式 TODO 接 RBAC。"""
    return user_id          # ← 直接返回，没有任何检查
```

也就是说知识库的 admin 接口（改模型配置、编 schema、动 gap-queue）**任何登录用户都能调用**。同时 `APP_ENV=dev` 下连令牌都不用带——`get_current_user_id` 会自动取第一个活跃用户。

绘图侧的 RBAC 是真实的（`user.role != "admin"` → 403）。合并后认证权威归知识库，这个空壳就成了整个系统的安全短板。

**必须在 P2 阶段一并补掉，不能推迟到后面。**

## 6. 接线设计

### 6.1 前端路由

```
前端 :5180（唯一入口）
  /                → portal 门户首页，两个平台入口
  /kb/*            → 知识库（问答 / 图谱 / wiki / digest / growth）
  /chart/*         → 绘图（模板中心 / 编辑器 / 产线平衡 / admin）
  /login           → 唯一登录页
```

两边原本各有登录页（知识库有 `Login.vue` + `Register.vue`，绘图有 `/login`），合并后收敛成一个。

### 6.2 API 代理（vite dev）

**顺序重要，具体路径必须在前：**

```
/api/chart   → :8010    重写 /api/chart → /api
/static/announcements|lb|sop|lbvideo → :8010
/api         → :8000    知识库原样，不改
/static/uploads → :8000
```

静态目录天然不冲突：知识库只挂 `/static/uploads`，绘图挂 `announcements` / `lb` / `sop` / `lbvideo`，按子路径分流即可。

**知识库后端完全不动**（你还在改它，这点很重要）。需要改的只有绘图前端的 axios `baseURL` → `/api/chart`。

### 6.3 响应格式不做统一

既然是双后端，前端保留**两个 axios 实例**，各带自己的拦截器：

- `/api/chart` 实例：拆 `{code, message, data}` 信封
- `/api` 实例：直接拿裸 Pydantic 对象

**99 个知识库接口一个都不用改。** 不要为了"格式统一"去重构两边的返回结构，那是纯成本没有收益。

### 6.4 生产环境 nginx

```
/api/chart/v1/*  → chart-api:8000/api/v1/*     （容器内仍是 8000）
/api/v1/*        → kb-api:8000/api/v1/*
/static/announcements|lb|sop|lbvideo → chart-api
/static/uploads  → kb-api
/                → 前端 dist，SPA fallback
```

## 7. 数据库方案

**一个 MySQL 实例（3306），里面开两个库。**

```
MySQL 实例（一个）
├── 库 kg_qa_ie   ← 知识库业务：users / wiki_pages / documents / qa_sessions ...（19 表）
└── 库 zhihuitu   ← 绘图业务：chart_records / templates / lb_* ...（13 表）

Redis 实例（一个）    仅绘图侧使用
Neo4j / Chroma        仅知识库侧，可选，第一阶段可不启
文件系统              wiki 的 .md 原文 + chroma 向量库，不进数据库
```

### 三条规矩

1. **`users` 以 `kg_qa_ie` 库为唯一权威。** 绘图库里涉及用户的表只存 `user_id` 整数，不做跨库外键（MySQL 本身也不支持跨库外键，这是正常做法而非妥协）。

2. **绘图后端不需要读知识库的用户表。** 登录由知识库签发 JWT，绘图侧拿同一密钥**验签**即可——验签是纯数学运算，不查库。令牌里已带 `sub`（user_id）和 `role`，够用。

3. **向量库和 wiki markdown 原文不要塞进 MySQL。** 它们本就是文件形态，入库只会让备份和检索都变难。数据库里只存"文件在哪、何时处理、状态如何"这类索引信息。

> 说明：早期曾判断知识库用的是 SQLite，需要迁移。**实际它已经在用 MySQL**（`mysql+pymysql://kgqa:CHANGE_ME@localhost:3306/kg_qa_ie`），所以**不存在迁移这一步**，两库同实例并存即可，成本比预估更低。

### 库名保持原样

两个库沿用原名 `kg_qa_ie` 和 `zhihuitu`，这样两边的连接串配置改动最小。

## 8. 登录打通

**知识库当签发方。** 改动集中在三处：

1. **共享 JWT 密钥**：知识库的 `jwt_secret` = 绘图的 `SECRET_KEY`
2. **绘图侧 `get_current_user` 改造**：用户查不到时**不再返回 401，而是按令牌里的 id / username 补一行影子记录**。这样绘图现有的所有外键都不用改。
3. **补知识库的 `require_admin`**，并关掉 `APP_ENV=dev` 的免登录旁路

### 两个必须注意的细节

**令牌有效期不一致。** 知识库令牌只有 60 分钟（配 14 天 refresh），绘图原本是 7 天且**没有 refresh 机制**。所以绘图前端的 401 处理要接上知识库的刷新流程，否则用户会在一小时后莫名被登出。这是本阶段的主要工作量。

**角色传递方式。** 建议知识库签发时用 `extra_claims` 把 `role` 塞进令牌（`create_access_token` 已支持该参数），绘图侧直接信令牌里的角色。这比两边同步角色表简单得多。

### 老用户密码不用重置

知识库用 argon2，绘图用 bcrypt。把知识库的 `CryptContext` 改成 `schemes=["argon2", "bcrypt"]`，验证时兼容 bcrypt 旧哈希，`deprecated="auto"` 会在下次登录时自动升级成 argon2。

## 9. 前端版本方向（反直觉的取舍）

主干是知识库，但**知识库前端是旧的**（JS / Vite 5 / Pinia 2 / EP 2.8），**绘图前端是新的且更大**（TS / Vite 8 / Pinia 3 / EP 2.13，45 文件 / 9.3K 行 vs 知识库 10 个页面）。

**不要把绘图降级到 Vite 5 + JS** —— 那等于把 9.3K 行 TypeScript 往回改。

**反过来做**：仓库仍以知识库为主干，但**前端外壳升级到 Vite 8 + TS + Pinia 3**，`tsconfig` 开启 `allowJs`，知识库那 10 个 JS 页面原样编译、不用改写。

工作量集中在：

- vite 5 → 8 配置调整
- Pinia 2 → 3（`defineStore` 写法未变，基本平移）
- Element Plus 2.8 → 2.13（小版本，风险低）

**性能注意**：知识库的 3D 图谱依赖（`three` 0.169 / `3d-force-graph` 1.73 / `force-graph`）体积很大，合并后必须单独切 chunk + 路由懒加载，否则会拖慢门户首页首屏。

## 13. 领域协同（为什么值得合并）

绘图侧的 `SOP_产线平衡集成_扩展计划.md`（v1.0，2026-06-03）规划了两块能力：

1. **产线平衡算法** —— 基于 DFS 的工人 / 工序分组优化
2. **SOP 生成系统** —— 工序编码 + 从视频分析生成标准作业文件

已落地 6 张领域表：`lb_styles` / `lb_processes` / `lb_stations` / `lb_plans` / `lb_cutpieces` 等，前端有 `/line-balance-studio` 工作台。

这些概念（产线、工位、工序、裁片、标准工时）**正是知识库的知识域**。该计划书没有提到知识库项目，但领域重叠度很高——合并后产线平衡可以直接引用知识库里的方法论与标准，知识库的问答结论可以直接出图。这是 P4 的价值所在，也是"做成一个系统"而非"两个站点共用登录"的理由。
